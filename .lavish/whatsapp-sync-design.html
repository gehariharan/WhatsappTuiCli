01 · System boundary

A small service with one ingestion path

Implementation choices

  • Standard library flag, net/http, slog, database/sql and embedded SQL migrations.
  • mattn/go-sqlite3 with the sqlite_fts5 build tag; a C compiler is required to build. Distributed output is a native executable. Driver documentation.
  • Small terminal QR renderer; environment variables and flags for MVP configuration. YAML can follow if useful.
  • Local data under os.UserConfigDir()/wasync, overridable with WASYNC_DATA_DIR.

Module responsibilities

cmd/wasync handles commands. internal/whatsapp wraps upstream APIs; internal/sync filters and normalizes; internal/storage owns transactions and migrations; internal/api serves queries; internal/config resolves flags and environment.

Protocol protobuf types stop at the adapter boundary. Storage and API use our own normalized types, making future exports or cloud replication additive.

03 · Pairing & consent boundary

Selecting a group must precede archiving its messages

Proposed first-run flow

  1. wasync login acquires the device lock and displays a terminal QR code.
  2. After authentication, fetch and save group IDs and names with capture disabled.
  3. Display groups and offer a terminal selection before login exits. Noninteractive users use groups enable.
  4. wasync run reuses the session, refreshes discovery and starts capture plus the loopback API.

Users who already know a group ID can enable it before login. History delivered after enablement uses the same allowlist.

The initial-history tradeoff

History arriving before group selection is discarded without writing message bodies or retaining an all-group history spool.

Enabling a group affects subsequently delivered live and historical events. It cannot guarantee that pairing history will be replayed. A login that exits early can also miss later history chunks.

Record enabled_at and coverage=unknown. The earliest stored timestamp only describes what we have.

Default: strict archival allowlist, best-effort history. An optional bounded in-memory selection buffer could improve first-run imports, but adds privacy and resource semantics; it is excluded from the initial design.

04 · Durable data contract

Stable identities, atomic changes, readable SQL

TableIdentity and essential fields
accountsLocal integer ID, canonical own-account JID, created_at. Reuse this account on re-pairing; a different account gets an isolated namespace and disabled groups.
groupsPrimary key (account_id, group_id); name, sync_enabled default false, enabled_at, last_message_at, created_at, updated_at. Discovery updates must preserve allowlisting.
messagesInteger local id for API and FTS; UNIQUE (account_id, group_id, message_id). Sender JID and alternate JID when provided; original timestamp, received_at, message_type, text_content, is_from_me, reply_to_message_id, safe media_metadata JSON, edited_at, deleted_at, source.
message_mutationsTarget composite message key; mutation identity, kind, protocol timestamp and minimal normalized payload. Needed for edits/revokes arriving before the original. Unique mutation key prevents repeat application; avoid an unfiltered raw-event dump.
sync_stateKey (account_id, group_id); last_received_at, last_history_sync_at, earliest_message_at, history_state, coverage_state, last_error. History state: not_observed / processing / idle / failed. Idle only means no import running.
sync_gaps & service_stateGap start, end and reason, scoped to affected enabled groups. Service instance heartbeat, clean_shutdown, connection state. A gap end marks resumed observation, not verified recovery.
history_batchesAccount, batch identity or hash when no stable upstream ID is usable, sync type, supplied chunk/progress metadata, observed/imported/skipped/failed counts and local processing state. Never interpret supplied progress as archive completeness.
messages_ftsFTS5 external-content index on current text using local message row ID. Insert/update/delete triggers synchronize it in the same transaction. Revoked text is cleared from the index.

Storage settings

Archive: WAL, foreign keys on every connection, busy timeout 5 seconds, synchronous FULL. One write connection; a small read-only pool for API queries. Keep read transactions short.

Numbered embedded migrations run under the process lock before service readiness. Track applied version; fail clearly on unsupported newer schemas. Device migrations remain owned by whatsmeow.

Indexes: group/time/local ID; group/sender/time/local ID; account/received_at. UTC Unix milliseconds internally; RFC3339 timestamps in API responses.

SQLite WAL · FTS5

Read from your own applications

Provide a documented archived_messages view with stable field names. Open SQLite read-only and filter by account and group. External programs must not modify archive tables or migration state.

Copying into another DB should use repeated snapshots/upserts keyed by account/group/message ID, or a later change-log API. A timestamp cursor alone can miss edits, late history, and deletions.

Use SQLite's backup API or stop the service before copying. Copying only the live .db file can omit WAL data.

05 · Processing rules

One accepted event, one transaction

Capture pipeline

  1. Check group JID and active account. Discard private chats, statuses, newsletters and disabled groups.
  2. Normalize text, extended text and captions. Retain sender JIDs as opaque identifiers; preserve alternate LID/phone identities when supplied. Do not assume every sender JID is a phone number.
  3. Extract reply ID only, without persisting the embedded quoted body. Store media type, MIME, filename, size and dimensions where available; omit decryption keys, download URLs and raw thumbnails.
  4. Serialize into the bounded writer path. Recheck allowlisting inside the transaction so disabling a group blocks queued writes.
  5. Apply mutation ordering; commit message, FTS and progress together. Only then report local ingestion success.

Idempotency & ordering

  • Repeated base messages insert once. A historical base message must never replace newer edited content.
  • Edits target the original message ID and use protocol timestamps. Older edits lose; ambiguous equal timestamps retain current state and flag an anomaly.
  • A revoke creates a tombstone even when the original is absent. Later history cannot resurrect its text. Clear current text and sensitive media fields; retain minimal identity and deletion time.
  • Persist pending normalized edits only for enabled groups; consume them when the target arrives. Bound retention and expose unresolved counts.
  • Update last_message_at with the maximum original message timestamp, never with the last arrival order.

Mutation parsing must be exercised against actual pinned-version edit/revoke fixtures. Reactions and unknown message types get type metadata only initially. View-once media is not archived. Ephemeral-message retention remains a policy decision before Phase 2; the risk review recommends expiry-aware retention or skipping content whose expiry cannot be determined.

06 · Failure semantics

Being connected says nothing about missing messages

connection: onlinehistory: idlecoverage: uncertain

These can all be true at once. Every group begins with unknown completeness. No automatic transition sets “fully archived.”

Connection supervisor

Disable library automatic reconnect and let one supervisor retry transient failures with jittered exponential backoff: 1, 2, 4… seconds, capped at 60. Reset after a stable authenticated connection.

Logged-out, temporary-ban, outdated-client and replaced-session events stop automatic retry and surface an actionable state. Avoid reconnecting into a session ownership conflict.

Record outages and scheduled stops. On unclean restart, create an uncertain interval from the last heartbeat. Replayed history may fill records without proving the gap is closed.

Writes & shutdown

Keep queues bounded and history transactions small. Never silently drop accepted events. Backpressure is bounded; sustained saturation or DB failure marks the service degraded, disconnects capture and reports uncertain coverage.

Do not promise transport delivery exactly once or recovery after an acknowledgement-before-commit crash. SQLite guarantees atomic local commits; protocol replay remains best-effort.

Shutdown: stop accepting writes via API, disconnect WhatsApp, drain accepted work with a deadline, save final state, close DBs and release the lock. If draining fails, leave clean_shutdown false.

07 · Local interfaces

Use the CLI, HTTP, or read-only SQL

CommandOwnership and behavior
wasync login / logoutAcquire exclusive device lock; refuse while run owns it. Logout keeps archived messages and only reports success after unlink succeeds.
wasync runLock, migrate, open archive and device store, start API, connect and ingest. A second run exits clearly. No implicit QR flow in unattended run.
groups list [--refresh]Read cached metadata by default. Refresh uses the running service or temporarily acquires the device lock when stopped.
groups enable / disable IDUse the running API; otherwise acquire the archive mutation lock and update offline. Disable retains existing archive and stops future writes.
groups purge ID --confirmDisable and transactionally remove archived messages, mutation payloads, search entries and group progress. Retain minimal disabled metadata; report that backups and old file pages may still hold copies.
status / search "keyword"Query the service when available; read-only DB fallback when stopped. Offline status explicitly labels the saved heartbeat as stale.
HTTP contract
  • GET /health: process and database readiness, no message content. GET /api/status: connection, heartbeat, queues, errors, history and gap summary.
  • GET /api/groups and GET /api/groups/{id}; POST /api/groups/{id}/enable and /disable.
  • GET /api/groups/{id}/messages: limit default 50, max 500; opaque keyset cursor on original timestamp and local ID, newest first.
  • GET /api/messages/search?q=…: FTS5 literal token/phrase search by default, bounded query size; no raw SQL or unescaped FTS syntax.
  • GET /api/messages/{id}: local integer archive ID. The upstream message ID is returned as a separate field, avoiding ambiguity across groups.
  • Message and search filters: group, sender, from inclusive, to exclusive; RFC3339 UTC dates. Responses contain items and next_cursor. Search uses chronological keyset ordering for the MVP. Cursors validate query/filter scope.
  • Return 400 for invalid input, 404 for missing records, 409 for incompatible state and 503 for unavailable storage. Parameterized queries everywhere. Reads exclude revoked bodies.
Local security defaults

Bind only 127.0.0.1:8787; refuse non-loopback addresses in MVP. Generate a local bearer token in a 0600 file and require it for all /api routes. Reject foreign Host and Origin headers, enable no CORS, and never put tokens in URLs. Set timeouts, request body limits, and avoid request logging of search terms.

Private data directory 0700; precreate session and archive DB files 0600 with a restrictive umask so WAL/SHM files inherit protection. Exclude DBs, QR output and tokens from Git. OS permissions do not encrypt the archive at rest.

Log lifecycle, counts and sanitized errors through slog; no bodies, QR payloads, secrets or raw events. Do not call messaging or read-receipt APIs for application features; protocol acknowledgements remain library behavior.

Document participant consent and the unofficial library's compatibility, WhatsApp terms and account restriction risks. Keep backups private. A purge is logical deletion, not guaranteed forensic erasure.

Review update · architecture risks

The local architecture fits. Capture guarantees need tighter boundaries.

Go + whatsmeow + SQLite is a reasonable personal-use foundation. The hardest problems are upstream delivery, first-run history timing, and making failure visible. Adding more services would not resolve those limitations.

R1 · Critical · external limit

History and downtime may never be recoverable

Failure: the phone delivers only part of history, or a reconnect delivers no replay for an outage. The local DB cannot infer what is missing from timestamps or chunk progress.

Recommendation: describe this as a selected-group capture client with best-effort historical import. Keep coverage unknown or uncertain; report observed ranges and outage intervals. If complete backfill is essential, this protocol cannot be the sole archival source.

Before building capture: pair a real account and observe what history actually arrives. This is an experiment, not a completeness proof.

R2 · High · product decision

Selection after pairing can miss the best history window

Failure: the client discards the initial history before you can discover and enable groups. A later enable command does not guarantee replay.

Recommendation: keep login connected through discovery and terminal selection. Support preconfigured IDs. Make strict no-buffer behavior explicit in setup and report discarded-before-selection counts without bodies.

Revisit if history matters more: a bounded RAM buffer during selection could retain early events for up to five minutes and 64 MiB, dropping unselected content on timeout. Overflow and expiry must be visible. This is an optional policy change, not assumed authorization to capture every group.

R3 · High · delivery boundary

Atomic SQL does not prevent every lost message

Failure: WhatsApp delivery may be acknowledged before our archive transaction commits. A process crash in between can lose a message even with perfect deduplication.

Recommendation: minimize asynchronous buffering and persist accepted events promptly. Verify the pinned library's handler-success and acknowledgement ordering before selecting a callback strategy. Do not treat a success-returning handler as durable delivery without tracing it.

A disk inbox for accepted groups can help local replay, but cannot close a protocol acknowledgement gap by itself. Preserve the documented at-most-observed capture guarantee.

R4 · High · simplify lifecycle

Owning reconnect adds protocol lifecycle work

Failure: custom retry races with library pairing reconnects, shutdown or a replaced session. A network-only model may miss authentication and protocol state transitions.

Recommendation: validate QR-to-authenticated reconnect and terminal failures in Phase 1. Keep pairing behavior in the library. If strict exponential retry is negotiable, retain library reconnect for the MVP and observe its linear backoff. Otherwise use one tested supervisor and disable only the automatic network retry it replaces.

Decision needed: retain the stated exponential requirement unless you choose to relax it; the proposed supervisor is not yet validated.

R5 · High · privacy policy

Local archives can outlive disappearing messages

Failure: a durable archive retains text that WhatsApp participants expected to expire. A revoke may never be delivered, and a logical purge leaves copies in backups or old database pages.

Recommendation: choose and document a group retention policy before Phase 2. Conservative default: exclude view-once content and expire ephemeral text when a reliable deadline is supplied; skip ephemeral content whose expiry cannot be determined. Offer durable retention only as an explicit group setting.

Do not store raw protobuf dumps. Exclude media keys and quoted bodies; limit pending mutation retention. Filesystem permissions do not provide encryption at rest.

R6 · Medium · downstream correctness

Polling the DB needs update and deletion semantics

Failure: pulling only messages newer than the last timestamp misses edits, late imports, revocations and purges. Copying the DB file while WAL is active can also produce an incomplete snapshot.

Recommendation: the MVP supports read-only SQL and consistent snapshots. If your next step is incremental replication into another DB, add a monotonic changes table with upsert/delete operations in the same archive transaction. Preserve minimal deletion identities after purge, without message bodies.

A change feed is not implemented or promised by the current API. Snapshot replacement remains the correct MVP deletion-aware pull strategy.

R7 · Medium · semantic edge cases

Identity and mutation rules need real fixtures

Failure: LID/phone sender identities change, history replays after deletion, edits arrive out of order, or an unsupported wrapper hides the actual message type.

Recommendation: keep group/message composite identity stable, retain supplied sender aliases, and validate edit targets, revokes and wrappers against pinned protobuf fixtures. Equal timestamps and unknown mutation shapes surface anomalies; avoid guessing.

Do not put unique constraints on phone-number-shaped sender values or replace tombstones with old historical text.

R8 · Medium · operating burden

The MVP has more moving parts than the happy path

Failure: disk full, slow history batches, long SQL readers, CGO packaging, a process lock that is not released correctly, or incompatible upstream changes make capture appear healthy while it stalls.

Recommendation: add migrations, locks, backpressure, heartbeat and error reporting alongside the first writes. Fail loudly on disk errors. Keep bounded transactions and expose queue age. Test the target macOS build with FTS5 enabled.

Keep the dependency pinned and upgrades deliberate. Whatsmeow is unofficial; protocol breakage, terms and account restrictions remain external risks. A local bearer token protects against browser access but not another process running as your OS user.

Revisions I recommend before Phase 2

  1. Run a connectivity spike: pair, observe history, restart, interrupt network and check pairing reconnect behavior.
  2. Choose strict discard versus a bounded selection-time RAM buffer; document the history tradeoff.
  3. Trace acknowledgement ordering and minimize the time before a durable archive commit.
  4. Adopt an explicit ephemeral-message retention policy.
  5. Confirm whether your downstream DB needs incremental changes now or can pull consistent snapshots.

Phase 1 remains useful while these are resolved. Reconnect policy, retention and history behavior should be settled before claiming the capture phase is complete.

08 · Incremental delivery

Build a working vertical slice, then expand

Phase 1

Pair and rediscover after restart

Initialize Go module, pin upstream, terminal QR, protected sqlstore, process lock, login/logout, cached groups and refresh. Start the allowlist foundation immediately.

Gate: native binary compiles; manual QR pairing, group discovery and session reuse succeed. Document toolchain, CGO and setup. Requires your phone for the real pairing check.

Phase 2

Store selected live and historical text

Versioned schema, writer transactions, normalization, enable/disable, duplicate handling, history imports, edit/revoke ordering and gap records. Reliability basics belong here.

Gate: focused tests for filtering, duplicate live/history delivery, account isolation, disable races and out-of-order mutations. Manual selected/unselected group check.

Phase 3

Query the local archive

Loopback API and token, keyset pagination, filters, FTS5 triggers, status/search CLI, read-only SQL view and purge.

Gate: test pagination ties, search after edits/revokes/purge, invalid input and API access controls; build with the documented FTS5 tag.

Phase 4

Exercise failure and recovery

Complete reconnect supervisor, shutdown deadlines, heartbeat and crash detection, storage error behavior and operating instructions.

Gate: restart, simulated network outage, interrupted transactions and migration recovery tests; document uncertain history and backup handling. Optional launchd/systemd examples follow foreground operation.

Each phase ends with a compile check, focused tests and run instructions as requested. No cloud sync, media downloads, message sending, MCP, AI features or application frontend in the MVP.

09 · Review

Review the risks before capture implementation

The key product choice is strict group consent at first pairing, accepting that some early history may not be recoverable. The first code slice will establish pairing, persistent sessions and discovery before adding capture.
